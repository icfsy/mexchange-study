# 1. v1 的问题 → v2 的对策

这张表是 v2 的**唯一动机来源**。每条问题都在 v1 代码里验证过（见 v1 指南 7.2 节）。

| # | v1 的问题（已验证） | 根因 | v2 对策 | 阶段 |
|---|---|---|---|---|
| 1 | 结算失败只打日志，**订单簿已动、账本未动**，无补偿 | 没有事件日志，无法回放/补偿 | **Sequencer + Event Log**，失败可重放、可补偿 | P1 |
| 2 | 内存订单簿 + 数据库订单**两个写入者，无对账** | 缺少对账机制 | **Reconciliation Service** 周期对账（引擎状态 / 投影 / 账本） | P1 |
| 3 | **无确定性回放** → 无热备、无灾备、无监管复现 | 命令流未持久化 | Sequencer 持久化**命令日志**，撮合引擎纯确定性 | P1/P5 |
| 4 | 结算幂等**有竞态**（`fill_id` 预检查在事务外） | 去重与写入不在同一事务边界 | 去重移入事务内 + 唯一约束 + 明确的幂等键协议 | P0 |
| 5 | **手续费算出但不入账**，无收入科目 | 单边流水、无系统账户 | 引入**系统账户**，费用入账，账目资金守恒 | P0 |
| 6 | **单边流水，非复式记账**，无法自证资金守恒 | 无科目表 | 系统账户 + 资金守恒校验（对账的一部分） | P0/P1 |
| 7 | `balances.locked` **从未被写入**（死列） | 锁仓用负流水实现，列被遗留 | 删除该列，或改为真正的"未决预留"视图 | P0 |
| 8 | 结算在**热路径同步 HTTP** 调用，延迟被 DB 事务绑住 | 缺独立结算层 | **异步结算（消费事件流）+ Outbox** | P1 |
| 9 | `/internal/*` **无鉴权且被网关公开代理**，含无限 `mint` | 信任内网 + 错误暴露 | 内部网络隔离 + **服务间认证（mTLS / 服务令牌）**，网关不再代理内部路由 | P0 |
| 10 | **行情 `sequence` 传了但不用**，靠周期性快照兜底 | 无缺口检测与补齐 | **序号缺口检测 + 可请求重传 + 快照服务** | P4 |
| 11 | `ohlcv` **两个写入者**（accounts 与 market_data） | 投影职责不清 | 单一写入者：从事件流投影的读模型 | P1 |
| 12 | 盘前风控只有余额检查，**在 accounts 内同步做** | 无独立风控层 | **Risk Gateway**：内存投影 + 预留 + TTL | P2 |
| 13 | **无 FIX / 无会话序号 / 无重传** → 机构无法接入 | 缺会话层 | **FIX Gateway** + 持久化消息存储 | P3 |
| 14 | 单交易对硬编码、单进程撮合 | 无注册中心 | **Market Registry** + 按 symbol 分片 | P5 |
| 15 | **无控制面**：`Manual intervention required` 却无工具 | 无运维/风控面 | **Control Plane**：停牌、熔断、人工干预 | P6 |
| 16 | 无价格保护：一笔胖手指单可击穿市场 | 无市场层校验 | 价格笼子 + 最大单量 + 熔断 | P2/P6 |
| 17 | `matching_engine` 的 **bench 编译不过**、README 过期 | CI 不构建 benches | CI 必须构建并运行 benchmarks | P0 |
| 18 | Migration **手写数组，`007` 漂移** | 无版本表 | 引入带版本表的迁移工具 | P0 |

# 2. 设计原则

v2 遵循六条原则。每条都能回答"某个具体设计为什么这样"。

### 原则 1：命令与事实分离（Command / Event）
- **命令（command）**：意图，"我想下单"。可以被拒绝、可以被去重。
- **事件（event）**：事实，"这笔成交发生了"。**不可撤销**，只能被后续事件补偿。
- 所有状态都是事件的投影 → 可回放、可重建、可审计。

### 原则 2：关键路径上只放"必要且可预测"的东西
- 必须放在路径上：风控校验、序号分配、撮合。
- 必须移出路径：数据库事务、HTTP 往返、通知、行情聚合、KYC。
- 判据：**如果它失败会导致"成交已发生但状态未落"，它就不能在路径上同步做。**

### 原则 3：每个边界明确声明交付语义
不许出现"应该是 exactly-once 吧"。每个跨进程边界必须写明是 at-most-once / at-least-once / exactly-once（靠幂等实现效果上的 exactly-once），以及失败时的行为。见第 7 节。

### 原则 4：所有共享可变状态必须可枚举、可重建
v1 的教训是"内存里有个订单簿，但没有办法重建它"。v2 要求：**任何内存状态都能从日志重建**，重建时间必须被测过。

### 原则 5：确定性优先
撮合引擎不得依赖：当前时间、随机数、线程调度、外部服务、哈希表迭代顺序。时间戳等外部输入必须由 Sequencer 注入。

### 原则 6：先修正确性，再谈扩展性
P0/P1 解决的是"钱会不会错"；P5 解决的是"能不能扩"。**顺序不能反**——在一个会丢钱的系统上做分片，只是让丢钱变得更快。

## 3.1 与 v1 的形态差异（一图看懂）

| 维度 | v1 | v2 |
|---|---|---|
| 订单流 | 网关 → UDP → 撮合 | 网关/FIX → **风控** → **Sequencer** → 撮合 |
| 资金校验 | accounts 同步查库+锁 | **Risk Gateway 内存投影 + 预留** |
| 结算 | 撮合内**同步 HTTP** | **异步消费事件** + Outbox + 补偿 |
| 权威顺序 | 无（靠 UDP 到达顺序） | **Sequencer 命令日志** |
| 恢复 | 无 | **回放命令日志** |
| 行情 | UDP 全量/增量，无补齐 | **增量+序号+快照+重传**，可选组播 |
| 写入者 | `ohlcv` 两个写入者 | 单一投影写入者 |
| 记账 | 单边流水 | **复式 + 系统账户** |
| 接入 | WebSocket/JSON | + **FIX** |
| 控制面 | 无 | 停牌/熔断/人工干预/审计 |
| 交易对 | 硬编码 1 个 | **Market Registry** + 分片 |

# 4. 新增与改造组件详解

## 4.1 Sequencer + Command Log（**最重要**）

**解决**：问题 1、3 —— 无回放、无补偿、无热备。

**是什么**：订单流的第一站。它做三件事：
1. 给每条命令分配**严格递增、无缺口**的序号
2. **注入时间戳**（下游不许自己取时间 → 保证确定性）
3. **持久化**（这才是权威日志）

**为什么这是地基**：只要命令流有序且持久，下面这些能力**全都免费获得**：
- **热备**：备机订阅同一命令流并回放，状态与主机逐位一致
- **崩溃恢复**：重启后回放即可，无需导出内存快照
- **审计复现**：可以重演任意历史时段的撮合过程
- **补偿**：结算失败时，可以重放相关命令生成补偿命令（而不是"回滚"）
- **测试**：录制的命令流就是最好的回归测试集

**实现选型**（按复杂度递增）：

| 方案 | 适用 | 代价 |
|---|---|---|
| 单机文件 + fsync（顺序写） | 单机、演示→小规模 | 无高可用，需自己做副本 |
| **PostgreSQL 表 + 序列**（v2 推荐起点） | 已有的 Postgres 就能做 | 吞吐受限于单表写入，但可批量化 |
| Kafka / Pulsar / NATS JetStream | 真正的多消费者、多副本 | 多一套要运维的基础设施 |
| 自研 Raft 复制日志 | 极致控制 | **不建议**——这是基础设施，不是业务 |

> **建议**：v2 从 **Postgres 表 + 批量 fsync** 起步（复用现有依赖，运维成本为零），
> 等真到吞吐瓶颈再换 Kafka。**不要一上来就上 Kafka**——那会把"修正确性"变成"搭基础设施"。

**命令日志 schema 草图**：

```sql
CREATE TABLE command_log (
    seq            BIGSERIAL PRIMARY KEY,        -- 权威顺序，无缺口
    ts             TIMESTAMPTZ NOT NULL,         -- 由 Sequencer 注入，下游不得自取时间
    symbol         TEXT        NOT NULL,
    account_id     UUID,                         -- 匿名(机器人)命令为 NULL
    kind           TEXT        NOT NULL,         -- place | cancel | replace
    client_order_id TEXT,                        -- 幂等键（FIX ClOrdID 直接复用）
    payload        JSONB       NOT NULL,         -- 命令体
    risk_checked_at TIMESTAMPTZ NOT NULL,        -- 风控通过的时刻
    UNIQUE (account_id, client_order_id)         -- 幂等：同一客户单号只能出现一次
);
```

**注意 `UNIQUE (account_id, client_order_id)`**：这把幂等做成了**数据库约束**，
而不是应用层的"先查再写"。v1 的结算竞态（问题 4）正是"先查再写"的后果。

## 4.2 Event Log（事实流）

**解决**：问题 1、10、11。

从撮合引擎产出的**不可变事实**：`OrderAccepted` / `Fill` / `OrderCancelled` / `OrderFilled` /
`BookDelta`。要求：
- 全局或按 symbol 严格递增序号（**无缺口**）
- 只追加、不可修改
- 是**所有下游读模型和结算的唯一输入源**

有了它，问题 11（`ohlcv` 两个写入者）自然消解：K 线变成**从事件流投影出来的读模型**，
只有一个写入者。

## 4.3 Risk Gateway（盘前风控）

**解决**：问题 12、16、8。

**为什么不能放在 accounts 里同步做**（v1 的做法）：每单一次数据库事务 → 延迟高、
**且数据库不可用就无法下单**。真实交易所都走"内存投影 + 预留"。

**架构要点**：

| 要点 | 做法 |
|---|---|
| **投影** | 从命令/事件流消费，在内存维护 `(account, asset) → 可用余额/持仓`。可随时从日志重建 |
| **预留** | `可用 = 投影余额 − Σ 未决预留`；预留带 **TTL**，超时自动释放 |
| **串行化** | 按 `account_id` **哈希分片**到单线程执行器 → 同一账户的"检查+预留"天然串行，无锁、无竞态 |
| **确定性** | 预留 ID 由 Sequencer 序号派生，不用随机数 |
| **对账** | 周期性比对投影与账本；**发现漂移 → 进入安全模式（拒单）**，而不是继续放行 |
| **多活** | 投影可多副本；预留通过命令流复制 → 主备切换不丢预留 |
| **在关键路径上** | 风控必须在路径上（这是底线），但它是**内存操作**，不是数据库操作 |

**关键权衡**：投影是最终一致的，意味着**存在极短窗口**内风控看到的余额偏乐观。
业务上必须接受这一点，用两个机制兜底：
1. **账本层仍强制 `available >= 0`**（数据库约束）→ 真出现超卖，结算会被数据库拒绝
2. **结算失败 → 触发对账 + 安全模式** → 不让错误累积

> 这就是"最终一致 + 硬约束兜底"的组合。**不要指望投影永远正确，要保证错误一定会被发现。**

**检查项分层**（对应 `EXCHANGE_DOMAIN_NOTES.md` 第 6.2 节）：
- 连接层（限流、最大未成交单数）→ API Gateway / FIX Gateway
- 订单层（价格笼子、最大单量、最小名义额、自成交）→ **本组件**
- 账户层（余额、持仓、杠杆）→ **本组件** + 投影
- 市场层（涨跌停、熔断、停牌）→ Control Plane

## 4.4 FIX Gateway

**解决**：问题 13。

| 职责 | 说明 |
|---|---|
| **会话层** | Logon / Logout / Heartbeat / TestRequest；**会话级收发序号** |
| **消息存储** | 按会话持久化**出站**应用消息，才能响应 `ResendRequest(35=2)`。**这是与 v1 最大的差别** |
| **幂等** | `ClOrdID(11)` 直接作为 `command_log.client_order_id`；`PossDupFlag(43)` 标记重发 |
| **映射** | `NewOrderSingle(35=D)`→place；`OrderCancelRequest(35=F)`→cancel；`OrderCancelReplaceRequest(35=G)`→replace；`OrderCancelReject(35=9)`；`ExecutionReport(35=8)`←事件 |
| **状态重建** | 支持 `OrderMassStatusRequest(35=AF)`，让客户端重连后批量查状态，避免海量重传 |
| **DropCopy** | 独立只读会话，给风控/合规 |
| **交易日** | 会话序号每日重置 |

**关键含义**：这一层让网关**从"无状态转发器"变成"有状态且需持久化的会话服务"**。
FIX 的重量全在这里，不在消息解析。

**注意**：v1 里那个**已定义但未使用的 `OrderReplace = 0x03`** 正好是 FIX 改单需要的原语——
v2 里它会被真正用起来。

```sql
CREATE TABLE fix_session (
    session_id     TEXT PRIMARY KEY,
    next_out_seq   BIGINT NOT NULL,
    next_in_seq    BIGINT NOT NULL,
    trading_day    DATE   NOT NULL,
    state          TEXT   NOT NULL      -- active | logout | reset-required
);

CREATE TABLE fix_message_store (           -- 支持 ResendRequest
    session_id     TEXT   NOT NULL,
    seq            BIGINT NOT NULL,
    msg_type       TEXT   NOT NULL,
    raw            BYTEA  NOT NULL,        -- 原样保留，重发必须逐字节一致
    created_at     TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (session_id, seq)
);
```

## 4.5 Market Data Publisher + Market Data Gateway

**解决**：问题 10（序号不用、无补齐）。

**三件套必须齐全**（行业范式见 `EXCHANGE_DOMAIN_NOTES.md` 第 8.2 节）：

| 组件 | 作用 |
|---|---|
| **增量（incremental）** | 逐笔变化 + **严格递增序号**。走低延迟通道（可选 UDP 组播） |
| **快照（snapshot）** | 某序号对应的完整状态。用于首次同步与重新同步 |
| **重传（retransmission）** | 客户端发现序号缺口 → 按"(会话, 起始序号, 条数)"请求补齐 |

**协议设计要点**（借鉴 MoldUDP64）：
- 序号空间**按会话（交易时段）隔离**，会话 ID 每日更换 → 避免跨日序号混乱
- 空闲时发**心跳包**（0 条消息）→ 推进客户端期望序号，用于检测"卡住"
- 客户端行为：检测到缺口 → 先请求重传；重传不可用 → 拉快照
- **服务端必须能回答"我发过序号 N 吗"** → 需要一段可查询的出站缓冲

**与 v1 的关键差异**：v1 靠"每 10 次 tick 发快照"被动兜底，**没有缺口检测也没有补齐**。
v2 让 `sequence` 真正参与正确性，而不是装饰。

**可选优化**：行情扇出与订单通道**物理隔离**（v1 是合并在一个网关进程里的）。
海量订阅者的连接管理不应影响下单延迟。

## 4.6 Settlement Service（异步结算）

**解决**：问题 8、1、5、6。

**核心变化：结算从"撮合热路径里的同步 HTTP"变成"消费事件流的异步服务"。**

```
Event Log ──► Settlement Service ──► (事务) ──► Ledger
                    │
                    └──► 失败 → 重试 / 补偿 / 报警，但不阻塞撮合
```

**为什么可以异步**：因为订单簿已经不是"唯一事实"了——**事件日志才是**。
成交一旦进入事件日志，就已经是不可撤销的事实；结算只是把它反映到账本上，**迟早会成功**。
这正是 v1 缺失的那个基础（v1 没有日志，所以只能在路径上同步结算，失败就彻底不一致）。

**三条必须做对的机制**：

1. **幂等**：`fill_id` 去重必须在**事务内**用唯一约束完成，不是先查再写（修掉问题 4）。
2. **Outbox 模式**：如果要对外发通知/写其他存储，与账本写入放在同一事务的 outbox 表，
   由独立进程投递 → 避免"账本写了、通知没发"。
3. **补偿而非回滚**：事件是不可撤销的。结算出问题就发**补偿分录**（红冲），
   而不是试图撤销历史。这也顺带解决了 v1 那个"`restore_order` 没人调用"的悬空设计。

## 4.7 Reconciliation Service（对账）

**解决**：问题 2、6。

**三个状态必须周期比对**：

| 比对 | 发现什么 |
|---|---|
| **账本 ↔ 余额投影** | 风控是否漂移（漂移 → 安全模式） |
| **事件日志 ↔ 账本** | 是否有成交未结算（遗漏） |
| **命令日志回放 ↔ 引擎内存状态** | 引擎是否与权威历史一致（检测非确定性 bug） |

**第三条尤其重要**：它是**确定性的测试**。如果定期回放命令日志得到的订单簿与线上不一致，
说明撮合引擎里有非确定性因素（哈希顺序、时间、并发）——这是必须立刻知道的严重问题。

**资金守恒校验**（对应问题 6）：把复式记账的"全部科目净额为零"变成一个定时断言。
**这是单边流水做不到的**——v1 无法自动证明"钱没多也没少"。

## 4.8 Control Plane（控制面）

**解决**：问题 14、15、16。

v1 里那句 `INCONSISTENCY ... Manual intervention required` 的荒诞之处在于：
**系统要求人工干预，却没给人任何工具。** Control Plane 就是那个工具。

| 能力 | 用途 |
|---|---|
| **停牌 / 恢复**（halt / resume） | 技术故障、异常行情、监管要求 |
| **熔断配置** | 涨跌幅阈值、静态/动态熔断参数 |
| **价格笼子配置** | 每品种的 ±X% 限制 |
| **订单/账户查询** | 事故排查 |
| **强制撤单** | 某账户异常时清掉其挂单 |
| **人工调账** | 走**双人复核 + 完整审计**的补账流程（绝不直接改余额） |
| **安全模式开关** | 对账发现漂移时手动/自动进入 |
| **审计查询** | 按账户/订单/时间查完整事件链 |

**设计原则**：Control Plane 的每个动作本身也要**写进日志**，并且**不绕过账本**
（要调账就产生分录，不直接 UPDATE 余额）。

## 4.9 Market Registry（交易对注册中心）

**解决**：问题 14。

v1 把 `KCN/EUR` 硬编码在 `SYMBOL` 环境变量里。v2 需要一张表：

```sql
CREATE TABLE market (
    symbol           TEXT PRIMARY KEY,
    base_asset       TEXT NOT NULL,
    quote_asset      TEXT NOT NULL,
    price_scale      INT  NOT NULL,        -- 价格小数位
    qty_scale        INT  NOT NULL,        -- 数量小数位
    tick_size        NUMERIC NOT NULL,     -- 最小价格变动
    lot_size         NUMERIC NOT NULL,     -- 最小数量变动
    min_notional     NUMERIC NOT NULL,     -- 最小名义金额
    maker_fee_bps    INT  NOT NULL,
    taker_fee_bps    INT  NOT NULL,
    price_band_pct   NUMERIC,              -- 价格笼子
    status           TEXT NOT NULL,        -- active | halted | closed
    engine_shard     INT  NOT NULL         -- 路由到哪个撮合分片
);
```

有了它，网关可以**按 symbol 路由**命令到对应撮合分片（问题 14）。

| 表 | 新增/变更 | 用途 |
|---|---|---|
| `command_log` | **新增** | 权威命令顺序 + 幂等 |
| `event_log` | **新增** | 不可变事实流 |
| `risk_reservation` | **新增** | 预留（也可只在内存 + 日志，不落表） |
| `account_ledger` | **改造** | 引入 `system_account` 概念，费用入账，可校验守恒 |
| `outbox` | **新增** | 事务性发件箱 |
| `fix_session` / `fix_message_store` | **新增** | FIX 会话与重传 |
| `market` | **新增** | 交易对注册 |
| `balances.locked` | **删除** | v1 的死列（问题 7） |
| `ohlcv` | **改为投影** | 单一写入者，从 `event_log` 投影（问题 11） |
| 迁移工具 | **替换** | 带版本表的迁移（问题 18） |

**账本改造要点**（复式记账最小可行版）：

```sql
-- 每个"账户"包括用户账户与系统账户
CREATE TABLE account (
    id       UUID PRIMARY KEY,
    kind     TEXT NOT NULL,          -- user | system_fee | system_mint | system_clearing
    owner_id UUID                    -- kind=user 时指向 users
);

-- 分录：一笔业务 = 至少两条台账，借贷净额为零
CREATE TABLE journal_entry (
    id          UUID PRIMARY KEY,
    txn_id      UUID NOT NULL,       -- 同一笔业务共享
    account_id  UUID NOT NULL REFERENCES account(id),
    asset       TEXT NOT NULL,
    amount      NUMERIC NOT NULL,    -- 正=借，负=贷（约定统一即可）
    entry_type  TEXT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL,
    -- 不变式：SELECT txn_id, asset, SUM(amount) FROM journal_entry GROUP BY 1,2 应恒为 0
);

-- 哈希链（防历史篡改）
ALTER TABLE journal_entry ADD COLUMN prev_hash BYTEA, ADD COLUMN hash BYTEA;
```

**资金守恒校验**（定时任务）：

```sql
-- 每个 (asset) 所有账户净额必须为 0，否则报警
SELECT asset, SUM(amount) FROM journal_entry GROUP BY asset HAVING SUM(amount) <> 0;
```

这条 SQL 是 v1 **做不到**的事情——这就是复式记账的价值。

# 6. 关键流程时序

## 6.1 下单（v2 全链路）

```
① 客户端 → API Gateway / FIX Gateway
      浏览器: WS private/place_order
      FIX:    NewOrderSingle(35=D), ClOrdID=C1

② 网关层校验（连接层风控）
      认证、限流、最大未成交单数、会话权限

③ 命令规范化
      生成/透传 client_order_id（浏览器侧由网关生成 UUID；FIX 侧直接用 ClOrdID）
      ⚠ 这一步之后，同一条命令的重复提交必须能被识别

④ Risk Gateway（内存，微秒级）
      - 按 account_id 分片路由到单线程执行器
      - 价格笼子 / 最大单量 / 最小名义额 / 自成交检查
      - 可用余额 = 投影余额 − 未决预留
      - 通过 → 创建预留(id 由序号派生, TTL)
      - 拒绝 → 立即返回错误（Reject ExecutionReport / JSON-RPC error）

⑤ Sequencer
      - 分配 seq、注入 ts
      - 持久化到 command_log（含幂等唯一约束）
      - ⚠ 到此为止，交易意图已成为"权威历史"的一部分

⑥ Matching Engine（对应 symbol 的分片）
      - 从命令流顺序消费
      - 纯确定性撮合 → 产出 Fill / OrderAccepted / OrderCancelled / OrderFilled
      - 不做任何 IO

⑦ Event Log
      - 事实流持久化、序号无缺口

⑧ 并行扇出
      ├─ Market Data Publisher → 增量+序号 → 网关 → 客户端
      ├─ Settlement Service    → 消费成交 → 释放预留 + 写账本
      └─ Read Model 投影       → OHLCV / 持仓 / 成交历史

⑨ 回报客户端
      - FIX: ExecutionReport(35=8)  浏览器: JSON-RPC 响应 + 私有事件推送
```

**与 v1 的四个关键差异**：
1. 风控在**内存**里做，不是数据库事务（延迟与可用性）
2. 命令**先持久化再撮合**（可回放、可恢复）
3. 结算**异步**（不再绑住热路径）
4. **预留**替代 v1 的"负流水锁仓"（语义更清晰，且能超时释放）

## 6.2 结算与补偿

```
① Settlement Service 消费 Fill 事件（至少一次）
② 事务内：
     - 幂等检查：INSERT INTO trades(... exchange_fill_id ...) ON CONFLICT DO NOTHING
       （必须在事务内、在写分录之前，用 RETURNING 判断是否首次）
     - 若首次：写分录（买方、卖方、系统手续费账户）
     - 释放对应预留
     - 写 outbox（如需通知）
③ 提交
④ 失败处理：
     - 可重试错误 → 退避重试（不阻塞撮合）
     - 不可重试错误 → 报警 + 该事件标记为"待人工"
     - 绝不"回滚订单簿"——事实已发生，只能补记
⑤ 对账任务发现"事件日志有成交、账本无分录"超过阈值 → 报警 + 安全模式
```

## 6.3 行情缺口恢复

```
客户端收到 seq=100, 下一个是 seq=103
   │
   ├─ 检测到缺口 [101, 102]
   ├─ 向重传服务请求 (session, 101, 2)
   │      ├─ 服务端命中出站缓冲 → 补齐 → 继续
   │      └─ 服务端未命中（太旧）→ 客户端拉快照
   └─ 若重传服务不可用且缺口持续 → 拉快照（最后手段：重新同步）

服务端心跳：空闲时发 0 消息包，携带当前 seq
   → 客户端据此判断"没消息"而不是"链路断了"
```

## 6.4 FIX 会话重连与重传

```
① 客户端重连，发 Logon(35=A)，携带自己期望的服务端序号 N
② FIX Gateway 比对 next_out_seq：
     next_out_seq <= N  → 无需重传
     next_out_seq >  N  → 从 fix_message_store 重发 [N, next_out_seq)
                          （重发消息置 PossDupFlag(43)=Y）
③ 若客户端序号落后：SequenceReset-GapFill(35=4, 123=Y) 或要求客户端重传
④ 客户端可用 OrderMassStatusRequest(35=AF) 批量重建订单状态，
   避免依赖海量 ExecutionReport 重传
```

## 6.5 崩溃恢复

```
撮合引擎崩溃
  ① 重启，从 command_log 的检查点回放（或从头回放）
  ② 得到与崩溃前逐位一致的订单簿
  ③ 期间 Risk Gateway 继续接受命令（因为它有投影），只排队不撮合
  ④ 追上进度后恢复撮合

整个恢复过程的重放时间必须被测量并写入运维手册
（这是"内存状态可重建"原则的落地验收标准）
```

# 7. 一致性模型与故障语义

**这一节是 v2 的验收标准。每个边界都必须能填出一行。**

| 边界 | 交付语义 | 失败时行为 | 幂等键 |
|---|---|---|---|
| 客户端 → 网关 | at-most-once | 客户端重试 | `client_order_id` |
| 网关 → Risk Gateway | at-least-once | 重试；预留 TTL 兜底 | `client_order_id` |
| Risk Gateway → Sequencer | exactly-once（靠唯一约束） | 冲突 → 返回原结果 | `(account_id, client_order_id)` |
| Sequencer → 撮合引擎 | **完全有序**、at-least-once | 引擎按 seq 去重 | `seq` |
| 撮合引擎 → Event Log | exactly-once（同进程事务/顺序写） | 重启后从 checkpoint 重放 | `seq` |
| Event Log → 结算 | at-least-once | 重试；对账兜底 | `fill_id` |
| Event Log → 读模型 | at-least-once | 重放重建 | `seq` |
| 行情 → 客户端 | at-most-once + **可检测缺口 + 可补齐** | 重传或拉快照 | `seq` |
| FIX 出站 | at-least-once + **可重传** | 消息存储重发 | 会话 seq |
| 账本写入 | **恰好一次**（事务内唯一约束） | 拒绝 + 报警 | `txn_id` |

**三条铁律**：
1. **幂等键必须由更上游生成并全程透传**——不能每个组件自己造。
2. **去重必须和写入在同一事务/同一原子操作内**（v1 的竞态就是这么来的）。
3. **任何"至少一次"都必须配一个对账**——否则你只是把错误推迟到未来。

# 9. 刻意不做的事（边界）

架构设计的价值有一半在于**拒绝**。v2 明确不做：

| 不做 | 为什么 |
|---|---|
| **自研 Raft / 分布式共识** | 这是基础设施。用 Postgres/Kafka 等现成的。自研只会得到一个有 bug 的共识实现 |
| **一上来就上 Kafka** | 先证明 Postgres 表不够用。过早引入基础设施会把"修正确性"变成"搭平台" |
| **每个服务一个数据库** | 共享 Postgres 在 v2 阶段仍然合理。等到写冲突或扩容真的成为瓶颈再拆 |
| **Kernel bypass / FPGA / 自研网卡驱动** | 收益是微秒级，成本是极高的复杂度。先让系统**正确**，再谈极限性能 |
| **在撮合引擎里做风控** | 撮合必须保持纯粹、确定性、无 IO。风控放前置的独立服务 |
| **在撮合引擎里做清算/保证金** | 除非做衍生品。现货的结算是记账，不是清算 |
| **把行情做成"可靠传输"（重造 TCP）** | 行情本来就可以丢。正确做法是"可检测 + 可补齐"，不是"不丢" |
| **直接改余额的"人工修复"** | 只能通过分录调账。任何绕过账本的修复都会破坏可审计性 |
| **微服务化到极致** | 服务数量和团队规模匹配。单人项目拆 20 个服务只会得到 20 份运维负担 |
| **blockchain** | 与本文档目标无关 |

**一条判断准则**：任何新增组件都必须能回答"**它消除了哪条已验证的问题？**"
答不出来就不要加。v2 第 1 节的表格就是这份"问题清单"。

# 10. 容量与延迟预算（设计目标）

⚠️ **以下是设计目标，不是本仓库的实测数据。** 列出它们是为了让取舍有量化依据。

| 环节 | 目标延迟 | 关键手段 |
|---|---|---|
| 网关层校验（认证/限流） | 10–50 µs | 本地 token 校验、内存计数 |
| **Risk Gateway（风控 + 预留）** | **50–200 µs** | 全内存、按账户分片、无锁 |
| **Sequencer 持久化** | **1–5 ms（批量）** | **批量 fsync**：牺牲单笔延迟换吞吐 |
| 撮合（单笔） | 1–10 µs | 纯内存、无分配热路径 |
| 事件发布 | 10–100 µs | 顺序写 + 扇出 |
| 行情到客户端 | 100 µs–1 ms | 增量 + 组播 |
| 结算落账（异步） | 10 ms–1 s | **不在关键路径上** |
| 崩溃恢复（回放） | 目标 < 60 s | 检查点 + 定期快照 |

**关键洞察**：**Sequencer 的持久化是新的瓶颈**，而且是**刻意接受**的。
v1 没有这个瓶颈，代价是没法恢复；v2 用几毫秒换"可回放"。
这就是第 2 节原则 2 的体现——**把延迟花在它值得的地方**。

**批量化是关键技巧**：单笔 fsync 可以到毫秒级，把 1000 笔批成一次 fsync 就能把摊薄成本降到微秒级。
代价是引入最多一个批次周期的延迟（等待窗口）——这又是"吞吐 vs 延迟"的经典取舍。

# 11. v1 → v2 组件映射表

| v1 组件 | v2 归属 | 变化 |
|---|---|---|
| `matching_engine`（库） | **保留** | 改为消费命令流、去掉自取时间、加参与者身份与 TIF 支持 |
| `udp_proto`（库） | **保留但改造** | 序号真正用于缺口检测；增加重传/快照消息类型；订单通道可选保留或换 TCP |
| `matching_engine_service` | **拆分** | 撮合部分保留（+确定性化）；订单簿发布拆到 Market Data Publisher；结算调用移除 |
| `gateway` | **拆分** | 订单入口保留为 API Gateway；行情扇出拆到 Market Data Gateway；读模型保留 |
| `accounts` | **拆分** | 账本/复式记账 → Ledger；下单校验 → Risk Gateway；结算 → Settlement Service |
| `market_data` | **降级为投影** | 不再是独立写入者，改为从 `event_log` 投影 OHLCV |
| `trading_bot` | **保留** | 仍是普通客户端；建议同时作为 FIX 客户端的测试方 |
| `frontend` | **保留** | 增加断线重连后的序号/快照重新同步逻辑 |
| — | **新增** | Sequencer / Event Log / Risk Gateway / FIX Gateway / Market Data Publisher / Settlement / Reconciliation / Control Plane / Market Registry |

## 落地建议

如果只能做一件事：**做 P0 + P1**。
它们不改拓扑、风险可控，但能把系统从"会丢钱且无法发现"变成"可回放、可对账、错误一定会被发现"。
**v2 的价值 80% 在前两个阶段**，后面的 P2–P6 是规模与机构接入的增量。

如果要论证这一点，可以反问：**在 P0/P1 完成前做分片（P5），除了让丢钱更快，能得到什么？**
