# 1. 撮合与分配：价格-时间优先只是选项之一

## 1.1 先分清"市场结构"，再谈撮合算法

很多人把"交易所"等同于"连续订单簿"，其实只有一类市场是这样：

| 市场结构 | 怎么成交 | 典型场景 | 有"时间优先"吗 |
|---|---|---|---|
| **连续限价订单簿（CLOB）** | 不断到达的订单与挂单即时撮合 | 股票、期货、加密现货 | 取决于分配算法 |
| **集合竞价（call auction）** | 在某时刻集中撮合，所有人同一个清算价 | 开盘/收盘、流动性差的品种 | **没有**（人人同价） |
| **RFQ / 询价** | 买方询价，多个做市商报价，择一成交 | 固收、FX、大额衍生品 | **没有** |
| **暗池（dark pool）** | 不公开订单簿，按参考价（如中间价）撮合 | 机构大单、减少市场冲击 | 弱 |
| **周期性拍卖 / 分批撮合** | 每隔固定间隔撮合一次 | 部分加密交易所、拍卖机制 | 取决于实现 |

**所以在讨论"撮合算法"之前，先确定市场结构。** 本仓库是单一交易对的 CLOB。

## 1.2 分配算法（allocation algorithm）对比

即使都是 CLOB，"同一价位上多个订单，新来的订单该跟谁成交、按什么比例"也有多种规则：

| 算法 | 规则 | 谁受益 | 典型使用者 |
|---|---|---|---|
| **FIFO / Price-Time** | 同价位按到达时间先后，先到先得 | 手速快、早挂单者 | 多数股票市场、加密现货 |
| **Pro-Rata** | 同价位按各单**挂单量比例**分配成交量 | 大单、做市商 | CME 的多数利率期货 |
| **Pro-Rata + Top Order** | 先给队列首位一部分（如 20–40%），剩余按比例分 | 兼顾时间优先与比例公平 | CME 部分产品 |
| **LMM / 指定做市商配额** | 给注册做市商额外分配额度 | 承担做市义务者 | 期权、部分期货 |
| **Split-Price / 混合** | 结合多种规则，或分价格档分配 | 视设计 | 各家不一 |
| **Allocation（人工/算法分配）** | 交易所按规则事后分配 | 视设计 | 部分衍生品 |

参考：[CME Supported Matching Algorithms](https://cmegroupclientsite.atlassian.net/wiki/spaces/EPICSANDBOX/pages/457218479/Supported+Matching+Algorithms)、[CME Globex Matching Algorithm Steps](https://www.cmegroup.com/confluence/download/temp/pdfexport-20190818-180819-0921-7924/EPICSANDBOX-CMEGlobexMatchingAlgorithmSteps-180819-0921-7925.pdf)、[Euronext Trading Procedures, Annex Three: Trading algorithms](https://www.euronext.com/sites/default/files/2019-10/Euronext%20Trading%20Procedures%20-%20Annexe%20Three%20-%20Trading%20algorithms%20-%20EN%20-%202019.10.18.pdf)。

> **关键结论：普适的不是"价格-时间优先"，而是"必须有一个事先公布、可预测、可复现的分配规则"。**
> 交易所可以选任何一种，但必须在交易开始前公开，并且对所有人一致执行——这才是"公平"的含义。

## 1.3 算法选择如何反向决定数据结构

这是对写代码最有价值的一节：

| 算法 | 需要什么数据 | 数据结构后果 |
|---|---|---|
| FIFO | 每个价位一个**有序队列** | 价格 → `VecDeque<Order>`（本仓库就是这样） |
| Pro-Rata | 需要每个价位上**所有订单的原始量与剩余量**，才能算比例 | 价格 → 订单列表 + 聚合量；分配时遍历、按比例取整、处理余数 |
| Top Order | 需要区分"队列首位"与其余 | 队列 + 首位特殊标记 |
| LMM 配额 | 需要订单上的**参与者身份与角色** | 订单必须携带做市商标识与配额账本 |

**所以：如果本仓库要支持 Pro-Rata，光改一个函数是不够的——`Fill` 要能表达"一个主动单同时与多笔挂单按比例成交"，`PriceLevel` 要保留每单原始量。** 这也是为什么"分配算法"是产品决策，不是实现细节。

## 1.4 成交价规则

- **连续 CLOB + FIFO**：成交价取**被动方（挂单方）价格**。主动方出价 105 撞挂着 100 的卖单，成交价 100——这叫**价格改善（price improvement）**，是市场惯例。
- **集合竞价**：只有一个清算价（使成交量最大的价格）。
- **RFQ / 暗池**：按约定的参考价（中间价、VWAP 等）。

本仓库取被动方价格，符合第一类。

# 2. 订单类型与有效期（TIF）

这是**最核心的业务逻辑**之一，也是本仓库最明显的简化所在。本仓库只有 `Limit` 和 `Market` 两种，**且没有 TIF**。

## 2.1 订单类型

| 类型 | 含义 | 撮合引擎要不要特殊处理 |
|---|---|---|
| **Limit** | 指定价格，未成交则挂单 | 否 |
| **Market** | 不指定价格，吃现有流动性，未成交部分丢弃 | 是（不挂单） |
| **Stop / Stop-Limit** | 触发价到达后才激活 | **是**（需要维护触发单簿 + 行情驱动触发） |
| **Iceberg / 隐藏单** | 只显示一部分数量，成交后补露 | **是**（一个逻辑订单多个显示切片） |
| **Post-Only** | 只做挂单，若会立即成交则拒绝 | 是（撮合前预判） |
| **Pegged** | 价格锚定买一/卖一/中间价，随行情移动 | **是**（需要行情驱动改价） |
| **Trailing Stop** | 追踪止损，触发价随价格上移 | 是 |

## 2.2 有效期（Time In Force, TIF）

| TIF | 含义 |
|---|---|
| **GTC**（Good Till Cancelled） | 一直有效直到撤销 |
| **DAY** | 当日有效，收盘自动撤销 |
| **GTD**（Good Till Date） | 到指定时间失效 |
| **IOC**（Immediate Or Cancel） | 立即成交能成交的部分，剩余**立即撤销** |
| **FOK**（Fill Or Kill） | 要么全部成交，要么全部撤销 |
| **GFA / GFS** | 立即成交、剩余挂单（部分交易所用） |

**IOC 和 FOK 是撮合算法的语义差异，不是参数差异**：FOK 要求引擎先**预演**一遍能不能全额成交（或用"全有或全无"的原子分配），才能决定是否执行。这会让撮合逻辑复杂度上一个台阶。

## 2.3 对本仓库的意义

本仓库的市价单行为（未成交部分丢弃 + 通知 accounts 撤销）**在语义上接近 IOC**，但：
- 没有 `order_type` 以外的 TIF 字段，所以无法表达 GTC/DAY/GTD；
- 没有 Stop / Iceberg / Post-Only；
- 没有订单过期（`expired` 状态在 CHECK 约束里声明了，但没有任何代码会设置它）。

**这三个缺失，是"玩具"和"能上线"之间的分界线之一。** 因为 Stop 单和 Iceberg 会改变撮合引擎的内部结构（要额外的触发簿、要隐藏量），不只是加字段。

# 3. 自成交防护（STP）

**自成交 = 同一个用户的买单和卖单互相成交。** 它看起来很傻，但会造成：
- 虚假成交量（制造活跃假象，可能构成市场操纵）
- 无意义的手续费消耗
- 在监控/合规上被视为可疑行为

## 3.1 常见策略

| 模式 | 行为 |
|---|---|
| **Cancel Resting** | 撤掉挂着的旧单，新单继续撮合别人 |
| **Cancel Incoming** | 拒绝/撤销新来的单 |
| **Cancel Both** | 两边都撤 |
| **Decrement / Cancel Oldest** | 只成交超出部分，或撤销较老的一单 |
| **Allow** | 允许自成交（部分加密交易所，为简化或为做市便利） |

## 3.2 实现前提

**自成交防护要求引擎认识"订单属于谁"。** 本仓库的 `Order` 和 `Fill` **只有订单 ID，没有用户 ID**，所以**结构上无法实现 STP**——这不是漏了一个函数，而是缺一层数据。

这是一个很好的例子：**一条业务需求（防自成交）会向上游要求数据模型变更（订单必须携带参与者身份），而不是在撮合函数里加个 if。** 真实交易所的撮合引擎通常携带 `participant_id` / `account_id`，即使引擎本身不做风控。

# 4. 金额、精度与记账

## 4.1 为什么禁止用二进制浮点表示钱

`f64` 是二进制浮点，无法精确表示 `0.1`、`0.2` 这类十进制小数。后果：

- `0.1 + 0.2 != 0.3`，累加误差随交易量放大
- 余额永远对不平，对账会持续产生"差几分钱"的悬空差异
- 舍入方向不确定，可能导致用户资金凭空增减

**这是行业铁律，没有例外。**

## 4.2 三种主流实现

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **语言原生 Decimal** | 如 Rust 的 `rust_decimal`、Java 的 `BigDecimal`、Python 的 `decimal` | 语义直观，十进制精确 | 比整数慢，有精度上限 |
| **定点整数** | 以最小单位存 `int64`（如"分"、"聪"）或按固定标度缩放 | **最快**，比较/运算无歧义 | 需要在边界显式换算；标度不匹配会出错 |
| **大整数 + 标度** | 自管理 `(unscaled_value, scale)` | 灵活 | 实现复杂 |

**撮合引擎内部常用定点整数**，因为性能敏感且只需比较和加减。这也说明：本仓库用 `Decimal` 是 Rust 生态下的合理选择，**不是唯一答案**。

## 4.3 精度分级：账务 vs 行情

一个很实用、也很常见的行业做法是**按数据用途分级精度**：

| 数据 | 精度要求 | 原因 |
|---|---|---|
| 余额、账本、成交金额 | **精确**（decimal / 定点整数） | 钱，必须对平 |
| 订单簿行情、K 线、指数 | **可以有误差**（浮点可接受） | 只用于展示和决策，不用于记账 |

本仓库正是这样做的：**UDP 线格式用 `f64`，账务用 `Decimal`**（见 `udp_proto/src/binary.rs` 的注释与转换点）。这个分级不是它发明的，是行业通行做法。

## 4.4 舍入与费用

- 每个币种有**最小精度**（EUR 2 位、BTC 8 位）。计算手续费、名义金额后必须**按币种舍入**，并明确舍入方向。
- **费用必须真的入账。** 本仓库算出 `FEE_RATE = 0.001` 并存进 `trades` 表，但**从未写入账本**——这意味着交易所没有收入科目，账目在"资金守恒"意义上不闭合（见第 5.4 节）。

## 4.5 单边流水 vs 复式记账（重要概念澄清）

这是最容易被混淆的一点：

| | 单边流水（single-sided ledger） | 复式记账（double-entry） |
|---|---|---|
| 一行代表 | 某个账户的一次增减 | 一笔交易的多条分录（借贷） |
| 余额 | 由流水推导，或另存投影 | 由科目余额汇总 |
| 自带校验 | **无**（加了才知道平不平） | **有**：全部科目净额恒为零，破坏了立刻能发现 |
| 前提 | 无 | 必须有**科目表**（chart of accounts），含系统账户 |
| 本仓库 | ✅ 是这样 | ❌ 不是 |

**真正的复式记账要求存在"系统账户/交易所账户"**，用户的每一笔变动都对应另一侧的分录。这样"钱既没多也没少"是一个可以自动验证的不变量，而不是靠人肉对账。

本仓库是**单边流水**：每行是一个用户的增量 + 滚动余额，没有系统账户。后果在机器人成交时最明显——被跳过的那一方**被凭空创造/销毁**（详见 v1 指南 7.2 第 11 条）。这在业务上意味着：**这个交易所的账目无法自证资金守恒**。

# 5. 可审计性与合规

## 5.1 传统市场 vs 加密市场

| | 传统受监管市场 | 加密交易所 |
|---|---|---|
| 记录保存 | **法规强制**，有明确保存年限 | 多数地区尚无同等强制 |
| 审计追踪 | **CAT（Consolidated Audit Trail）** 等国家级追踪系统 | 基本没有 |
| 交易前风控 | **强制**（券商侧） | 自愿 |
| 账本不可篡改 | 法定 + 技术双重 | 主要靠技术，且往往做得更弱 |
| 客户资产隔离 | 强制（且是近年监管重点） | 差异很大，事故频发 |

**所以"只追加账本"在传统市场是合规义务，在加密里更像良好实践。** 本仓库用数据库触发器强制不可改，方向对，但真实系统通常还会叠加：

- **WORM 存储**（Write Once Read Many）或对象存储的不可变版本
- **哈希链 / Merkle 树**：每条记录包含前一条的哈希，任何回溯修改都会破坏链条
- **异地只读副本**
- **导出归档**给监管方

## 5.2 监管依据

- 美国 **SEC Rule 15c3-5（Market Access Rule）**：要求有市场准入的券商实施**盘前**风险控制，且控制权必须在券商自己手中（不能外包给客户）。见 [SEC 最终规则](https://www.sec.gov/files/rules/final/2010/34-63241.pdf)。
- 欧盟 **MiFID II / RTS 6**：要求算法交易有盘前限额（价格、数量、名义金额、最大订单数、最大持仓）与事后监控。见 [ESMA 算法交易监管简报](https://www.esma.europa.eu/sites/default/files/2026-02/ESMA74-1505669079-10311_Supervisory_Briefing_on_Algorithmic_Trading_in_the_EU.pdf)。

## 5.3 审计要能回答的问题

一套可用的审计能力至少要能回答：
1. 这笔成交**为什么**发生？（当时的订单簿、触发它的命令）
2. 这个余额**怎么来的**？（完整流水链条）
3. 系统在某时刻的**完整状态**是什么？（快照 + 回放）
4. 有没有人**改过**历史？（哈希链校验）

第 3 条直接要求**确定性回放**——见下节。

## 5.4 确定性回放（determinism / replay）

**真实撮合引擎几乎都遵循同一个模式：**

> 输入一个**有序的命令流**，产生一个**确定的输出事件流**。相同输入必然得到相同输出，不依赖时间、随机数、线程调度或外部状态。

为什么必须这样：
- **热备/灾备**：备机只需回放同一命令流就能得到完全一致的状态，不需要复制内存
- **崩溃恢复**：重启后回放日志即可恢复，不需要定期导出内存快照
- **监管复现**：可以重演历史，证明某笔成交符合规则
- **测试**：用录制的命令流做回归

**本仓库恰好缺这一环**：订单簿只在内存里，没有命令日志，所以既不能回放，也不能做热备。这正是 v1 指南说的最大架构缺口，也是 v2 文档（`ARCHITECTURE_V2.md`）要解决的第一个问题。

# 6. 交易前风控（pre-trade risk）

## 6.1 唯一铁律

> **风控必须在订单到达撮合引擎之前完成。**

原因：撮合引擎一旦接受了订单，成交就已经发生、已经公告、已经进入市场数据流。事后补救意味着撤销一笔已经公开的成交——业务上不可接受，监管上也不允许。

## 6.2 风控是分层的

| 层 | 检查项 | 放在哪 |
|---|---|---|
| **连接层** | 限流、消息速率、最大未成交订单数、会话权限 | 网关 / FIX 会话层 |
| **订单层** | 最大单量、最小名义金额、价格笼子、最大偏离、自成交检查、Post-Only 检查 | 风控服务（紧邻撮合入口） |
| **账户层** | 可用余额、保证金、杠杆、持仓限额、单日亏损限额 | 风控服务 + **账户状态投影** |
| **市场层** | 涨跌停、熔断、halt、开收盘状态、交易时段 | 交易所控制层 / 撮合前置 |
| **组合层** | 跨品种风险、压力测试、VaR | 独立风控系统（可异步） |

组合层可以异步、可以慢；**前四层必须在关键路径上**。

## 6.3 最难的一点：账户状态从哪来

风控需要知道"这个账户还有多少钱"，但**数据库往返不能出现在热路径上**。两种路线：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **强一致** | 每次下单同步查库/事务 | 简单、天然正确 | 每单一个 DB 事务；延迟高；**数据库不可用就无法交易** |
| **投影 + 预留** | 风控服务在内存里维护余额/持仓**投影**，本地校验后**预留(reserve)**，预留作为事件写出，由账务异步落账 | 低延迟、可水平扩展、可多活 | 需要预留语义、幂等、超时释放、**与账本周期对账**；投影漂移会导致超额成交 |

**真实交易所几乎都走第二条。** 这也是"为什么交易所系统这么复杂"的根本原因之一。

关键配套机制：
- **预留（reservation）**：`可用 = 余额 − Σ 未决预留`，预留带 TTL，超时自动释放
- **投影（projection）**：从命令/事件流回放构建，可随时重建
- **对账（reconciliation）**：周期性比对投影与账本，发现漂移就进入安全模式（拒单）而不是继续放行
- **序列化**：同一账户的检查+预留必须串行（单线程分片 / 按账户哈希分片），否则会双花

# 7. 价格保护机制：价格笼子、涨跌停、熔断

这些是**保护市场不被单笔错误订单击穿**的机制，属于业务规则，通常由交易所控制层而非撮合引擎实现：

| 机制 | 作用 |
|---|---|
| **价格笼子 / Price Band / Limit Up-Limit Down** | 订单价格超出参考价的 ±X% 就拒单，防止胖手指 |
| **动态熔断 / Circuit Breaker** | 价格波动超过阈值时暂停交易 N 分钟 |
| **静态熔断** | 涨跌幅达到日限就停牌 |
| **Halt / 暂停交易** | 交易所主动暂停某品种（新闻、技术故障） |
| **最大单量 / 最小名义金额** | 防胖手指与粉尘单 |
| **Velocity Check** | 单位时间订单数/撤单数超限就限流（也防 spoofing） |

本仓库**一个都没有**。所以一笔 `price = 0.0001` 或 `quantity = 1e12` 的订单会被无条件接受并撮合。这是"能演示"和"能开放给真人"之间最危险的一条鸿沟。

# 8. 市场数据与订单流为什么分两条通道

## 8.1 真正的理由：通信拓扑，不是延迟

本仓库 README 给的理由是"减少 TCP 握手、避免队头阻塞"。**它只说对了一半**，而且对**订单**通道其实不成立（长连接没有握手开销，点对点也没有 HOL 竞争）。

真正的理由：

| | 行情（market data） | 订单（order flow） |
|---|---|---|
| 拓扑 | **1 → N**（扇出给成千上万订阅者） | **1 → 1**（点对点） |
| 丢包容忍度 | 可以丢（有恢复机制） | **不可以丢** |
| 有序性 | 需要（序号 + 补齐） | **必须严格有序** |
| 所以用什么 | **UDP 组播**（网络层复制，发送端只发一次，订阅者数量不影响发送端） | **TCP**（可靠、有序、有流控） |

**如果行情用 TCP**：服务端要为每个订阅者维护连接和发送缓冲；一个慢客户端会拖累服务端，甚至引发队头阻塞——而行情恰恰是最不能因为某个慢客户端而延迟的数据。

## 8.2 真实行情协议的三件套

所有真实行情流都由三部分组成，缺一不可：

1. **快照（snapshot）**：某个时刻的完整状态，用于首次同步和重新同步
2. **增量（incremental / delta）**：逐笔变化，带**严格递增的序号**
3. **恢复（recovery）**：检测到序号缺口时的补齐手段

**关键点：UDP 只用在不允许等待的"实时增量"上，"补历史"永远走另一条可靠通道。**

现成范式：

- **[Nasdaq MoldUDP64](https://raw.githubusercontent.com/Open-Markets-Initiative/Directory/refs/heads/main/Protocols/MoldUdp64.md)**：ITCH 行情流底下的传输层。UDP 组播 + 64 位序号 + 心跳（空闲时发 0 消息包，用于推进期望序号）+ **专门的 UDP 单播重传服务器**（接收方发现缺口后按"会话 + 起始序号 + 条数"请求重传）。会话 ID 每日更换，序号空间按会话隔离。
- **CME MDP 3.0**：同样 UDP 组播 + SBE 二进制编码，配 TCP recovery 通道。见 [CME MDP 3.0 Market Data](https://www.cmegroup.com/confluence/download/temp/pdfexport-20220521-210522-1838-33318/EPICSANDBOX-CMEMDP3.0MarketData-210522-1838-33319.pdf)。
- **SBE（Simple Binary Encoding）**：为行情设计的高效二进制编码，字段偏移固定、无需解析。

**对照本仓库**：它有 `sequence` 字段，但**网关不用它检测缺口**（我验证过）；它有周期性快照（每 10 次 tick），思路对，但**没有"可请求的补齐"**，只能被动等下一次快照。这就是 v1 指南说"恢复故事弱"的技术根源。

## 8.3 延迟预算与 colocation（背景知识）

真实交易所的延迟以**微秒**计，因此有：
- **Colocation**：客户把服务器放进交易所机房，网线直连
- **Kernel bypass**（DPDK、Solarflare/onload）：绕过内核网络栈
- **FPGA 网卡**：把部分逻辑下推到硬件
- **组播**：避免 N 份单播

这些是**为了省几微秒**的投入，量级和本仓库（容器内 UDP + 100ms 发布 tick）差 4–5 个数量级。理解这一点有助于你判断：**本仓库的"高性能"叙事更多是学习目标，而不是优化结果。**

# 9. 网关与会话层

## 9.1 通用模式：API Gateway

见 [microservices.io — API Gateway](https://microservices.io/patterns/apigateway.html)（我核对过内容）。核心职责与代价：

**职责**：单一入口、屏蔽服务分区与服务位置、协议转换（对外 Web 友好 / 对内任意协议）、认证、请求聚合扇出。
**代价（文档自己写的）**：多一次网络跳、多一个必须开发部署运维的部件。

## 9.2 交易所特有的：为什么常常是**两个**网关

| 网关 | 面向 | 特征 |
|---|---|---|
| **Order Entry Gateway** | 交易指令 | 连接少、消息重要、必须可靠有序、有会话状态、强风控 |
| **Market Data Gateway** | 行情 | 连接多、消息可丢、需要组播/扇出、有快照与恢复 |

**拆开的理由**：两者的负载特征、失败模式、协议、扩容策略完全不同。把它们放一起，行情的高连接数和高扇出会危及订单通道的稳定性——而订单通道是绝对不能抖动的。

**本仓库把两者合并在一个 `gateway` 进程里**（WebSocket 既发订单又推行情）。对演示项目合理；放到真实场景，行情扇出会直接影响下单延迟。

## 9.3 会话层要管什么

- 身份与会话绑定、权限
- **会话级序号**（用于断线重连后判断丢了多少）
- 心跳与超时（检测半开连接）
- 限流与配额
- **有状态**：谁的订阅、谁的订单、待发消息的缓存

最后一条很重要：**会话层一旦有状态，就需要考虑持久化与故障转移**——这正是 FIX 接入带来的重量（见第 10 节）。

# 10. FIX 协议

## 10.1 分层：FIX 不只是消息格式

```
┌─────────────────────────────────────────┐
│  应用层（Application）                    │  NewOrderSingle, ExecutionReport, ...
├─────────────────────────────────────────┤
│  会话层（Session / FIXT.1.1）             │  Logon, Logout, Heartbeat, TestRequest,
│                                         │  ResendRequest, SequenceReset
├─────────────────────────────────────────┤
│  传输层                                  │  TCP
├─────────────────────────────────────────┤
│  编码                                    │  tag=value（文本）/ SBE / FAST（二进制）
└─────────────────────────────────────────┘
```

**大部分难度在会话层，不在应用层。**

## 10.2 关键消息

| 消息 | tag | 用途 |
|---|---|---|
| `Logon` | 35=A | 建立会话，交换序号 |
| `Logout` | 35=5 | 结束会话 |
| `Heartbeat` / `TestRequest` | 35=0 / 35=1 | 保活与探测 |
| `ResendRequest` | 35=2 | **检测到序号缺口，请求重发** |
| `SequenceReset` | 35=4 | 序号重置（GapFill / Reset） |
| `NewOrderSingle` | 35=D | 下单 |
| `OrderCancelRequest` | 35=F | 撤单 |
| `OrderCancelReplaceRequest` | 35=G | **改单**（撤旧+下新） |
| `OrderCancelReject` | 35=9 | 撤单/改单被拒 |
| `ExecutionReport` | 35=8 | 订单回报（接单、成交、撤单、拒绝） |
| `OrderStatusRequest` | 35=H | 查询订单状态 |
| `OrderMassStatusRequest` | 35=AF | **批量查询**（重连后重建状态，避免大量重传） |
| `MarketDataRequest` | 35=V | 订阅行情 |
| `MarketDataSnapshotFullRefresh` | 35=W | 全量快照 |
| `MarketDataIncrementalRefresh` | 35=X | 增量 |

## 10.3 会话语义（真正的重量所在）

| 要求 | 含义 | 架构后果 |
|---|---|---|
| **会话级序号** | 收发各自维护严格递增序号，任何缺口都要处理 | 网关必须**按会话持久化序号状态** |
| **至少一次 + 可重传** | 收到 `ResendRequest` 必须能重发指定区间的消息 | **必须为每个会话维护持久化的出站消息存储（message store）** |
| **幂等** | `ClOrdID(11)` 相同的重复请求必须被识别 | 需要幂等键体系；`PossDupFlag(43)` 标记重发消息 |
| **交易日重置** | 每日会话序号归零 | 需要交易日概念与重置流程 |
| **DropCopy** | 给风控/合规的成交副本流 | 独立的只读会话 |

参考：[Eurex T7 FIX Gateway Manual](https://www.eurexgroup.com/resource/blob/1510770/c935164ab78e2dd9cc8c67264ad3437e/data/T7_FIX_Gateway_Manual_v.7.1.pdf)、[JSE Trading Gateway FIX 5.0](https://www.jse.co.za/sites/default/files/media/documents/2020-02/Volume%2002%20-%20Trading%20Gateway%20%28FIX%205.0%20SP2%29%20v3.03.pdf)、[ASX FIX Order Entry 规范](https://www.asxonline.com/content/dam/asxonline/public/documents/asx-trade-refresh-manuals/asx-trade-fix-order-entry-message-specification.pdf)（这几份都描述了序号缺口如何触发 Resend）。

> **结论：很多人以为"接 FIX = 加个 parser"。实际上难的是会话序号和重传存储——它会把网关从无状态转发器变成有状态、需持久化的会话服务。**

## 10.4 为什么行情不用 FIX

真实交易所几乎**不用 FIX 传高频行情**：
- 文本编码体积大、解析慢
- FIX 是点对点会话模型，**不支持组播**
- 行情需要的"快照+增量+序号+补齐"在 FIX 里表达得笨重

典型形态是 **FIX 接入订单 + 独立二进制/组播通道传行情（ITCH / MDP）**，两者并存，客户端可只用其一。

## 10.5 其他常见接入协议（背景）

| 协议 | 特点 |
|---|---|
| **FIX** | 行业通用、可读、跨厂商 |
| **ITCH / MDP / OUCH / iLink** | 交易所专有二进制，为性能设计 |
| **SBE / FAST** | 编码层标准，常与上面搭配 |
| **WebSocket / JSON** | 加密交易所主流，开发者友好但慢 |
| **gRPC / REST** | 管理类 API、非延迟敏感场景 |

# 11. 清算与结算

这是最容易和"保证金/风控"混淆的一组概念，业务上必须分清：

| 阶段 | 英文 | 做什么 | 谁做 |
|---|---|---|---|
| **成交** | Execution / Trade | 撮合产生成交记录 | 交易所撮合引擎 |
| **清算** | Clearing | 计算各方应收应付、净额、保证金要求 | 清算所（CCP） |
| **结算** | Settlement | 实际转移资产/资金（DvP：券款对付） | 结算系统 / 托管行 |
| **托管** | Custody | 持有资产 | 托管行 / 钱包系统 |

**关键业务差异：**

- **传统市场**：成交 → 清算（T+0 或 T+1）→ 结算（T+1/T+2），中间有**中央对手方（CCP）**做担保，还有**净额结算**（netting，把一天的应收应付轧差）。所以"结算"是一个独立、有自己账本的环节。
- **加密现货**：通常**成交即结算**（T+0，近乎原子）。因为没有 CCP，交易所直接改用户余额。
- **本仓库**：属于后者——`POST /internal/settle` 直接改余额。**没有清算层、没有 CCP、没有净额结算、没有保证金。**

**这对架构的含义：** 传统市场的"结算服务"之所以必须独立，是因为它有**净额、保证金、对手方风险**这些真正的业务；而加密现货的"结算"更像是"记账"。所以 v2 文档里我把"独立结算服务"的优先级排得比"事件日志"和"风控"低——**除非你要做衍生品**（那时保证金、强平、资金费率、保险基金全部需要，结算层就变成核心）。

# 12. 做市、手续费与流动性激励

## 12.1 Maker / Taker 与费率

| 角色 | 定义 | 通常 |
|---|---|---|
| **Maker** | 挂单方，提供流动性 | **费率低，甚至返佣（rebate）** |
| **Taker** | 吃单方，消耗流动性 | 费率高 |

**费率通常按 30 天交易量分档（fee tier）**，还可能按持仓量、是否做市商调整。

## 12.2 本仓库的情况

- 有 `FEE_RATE = dec!(0.001)`，且区分了 `buyer_fee` / `seller_fee`
- 但**没有 maker/taker 区分**（两边同费率）
- **没有费率分档**
- **手续费算出来了却从不入账**（不写账本），所以交易所实际上没有收入

**业务上这意味着：这个交易所不赚钱，也无法回答"我赚了多少手续费"这个问题。**

## 12.3 流动性激励的其他手段（背景）

- **返佣（rebate）**：给 maker 反向付费
- **做市商计划（MM program）**：承诺双边报价换取更低费率/配额
- **交易挖矿 / 返点**：加密圈常见
- **Imbalance / 收盘价激励**

这些都要求账本能表达"交易所 → 用户"的付款，也就是**必须有系统账户**——又回到第 4.5 节的复式记账问题。

# 13. 本仓库缺了哪些"标准件"

把上面的业务知识对照本仓库，可以列出一份"标准件清单"。**这不是 bug 列表，而是"玩具 vs 生产"的功能差距**：

| 业务能力 | 本仓库 | 补齐的业务影响 |
|---|---|---|
| 订单类型 | 只有 Limit / Market | Stop、Iceberg、Post-Only、Pegged 需要引擎结构升级 |
| TIF | **无** | GTC/DAY/GTD/IOC/FOK；FOK 需要原子全额成交 |
| 自成交防护 | **无（且缺少参与者身份，结构上做不到）** | 合规与反操纵基本要求 |
| 价格保护 | **无** | 一笔胖手指单可击穿市场 |
| 交易前风控 | 只有余额检查，在 accounts 内同步做 | 真实系统需要独立风控 + 内存投影 |
| 手续费 | 算了但**不入账** | 无收入、无资金守恒 |
| 复式记账 / 系统账户 | **无** | 无法自证资金守恒 |
| 确定性回放 | **无** | 无热备、无灾备、无监管复现 |
| 行情缺口补齐 | 只有周期性快照，**序号未使用** | 客户端可能静默失同步 |
| 会话序号 / 重传 | **无** | 无法支持 FIX 等机构接入 |
| 风控层级 | 只有账户层一部分 | 连接层/订单层/市场层全缺 |
| 多交易对 / 市场注册中心 | 单交易对硬编码 | 无法上第二个品种 |
| 冗余与故障切换 | **无**（全是单点） | 任何组件挂掉都停摆 |
| 交易所控制台 | **无** | 无法停牌、无法处理异常、无法人工干预 |

**最后一条（控制台）常被忽略但极其重要**：v1 代码里那句 `INCONSISTENCY ... Manual intervention required` 就是在呼唤一个不存在的东西——**运维/风控人员没有任何工具去执行这个"manual intervention"**。生产系统必须有一个能查、能停、能补的管理面。这一点我在 v2 文档里单独列了一节。
